How SSH bots take over accounts through authorized_keys

15 October 2026 · Jorge Aquino

Servers that accept SSH password logins from the internet get a steady stream of automated guessing. This post looks at what one common bot does once a guess works: it deletes every existing SSH key and installs its own.

Volume

Counts from one 24-hour window, 14 October 01:00 to 15 October 01:00 UTC:

That averages about 47 sessions per source address, which points to automated scanning rather than people.

The two commands that keep coming back

Over the seven days from 8 to 15 October, two multi-step patterns came up again and again, almost the same number of times:

cd ~ ; chattr -ia .ssh ; [EXECUTABLE] -ia .ssh

Seen 150 times in seven days.

cd ~ && rm -rf .ssh && mkdir .ssh && echo [SSH_KEY] >> .ssh/authorized_keys && chmod -R go= ~/.ssh && cd ~

Seen 146 times in seven days.

My publishing filter replaces anything that might be sensitive or unrecognized with a placeholder like [SSH_KEY], which is why you see those brackets. The two counts are nearly equal, and as the outside reports below show, other sensors record these commands back to back. My read is that they are two halves of one routine.

What each step does

  1. chattr -ia .ssh removes the immutable and append-only flags from the SSH folder. Admins, and rival bots, sometimes set those flags so the folder can't be changed. This step undoes that.
  2. [EXECUTABLE] -ia .ssh repeats the same flags with a program my filter didn't recognize, so it was replaced with a placeholder. Other honeypot operators record a program called lockr in this position, which their fake shells answer with "command not found." It looks like a backup in case chattr was renamed or removed.
  3. rm -rf .ssh deletes the folder, which removes every key that could already log in as this user. That locks out the real owner, and any competing bot, in one step.
  4. mkdir .ssh and echo [SSH_KEY] >> .ssh/authorized_keys recreate the folder with a single key: the attacker's.
  5. chmod -R go= ~/.ssh removes access for everyone except the owner. The SSH server ignores key files that other users can write to, so this step makes sure the new key is actually accepted.

The result: a password that was guessed once becomes key access that survives a password change. Rotating the password afterward doesn't remove the attacker. MITRE ATT&CK lists this as T1098.004, SSH Authorized Keys.

I'm not the only one seeing it

Other honeypot operators have recorded this same chain, step for step, for years. In public write-ups the planted key ends with the comment mdrfckr, which is how the campaign got its name (port22, 2023; DEV Community, 2026). Some researchers link it to the Outlaw (also called Dota) cryptomining group. Others say the bot is separate from that group. I'm not attributing it to anyone.

One limit is my own doing. I redact keys before publishing, so the public data on this page can't show whether my sensor received that exact key. My claim is that the commands match the published reports, nothing more.

Check your own servers

  • Read every authorized_keys file, including root's, and remove any key you can't account for. A quick first check: grep -r mdrfckr /root/.ssh /home/*/.ssh.
  • Turn off password logins for SSH with PasswordAuthentication no, and use PermitRootLogin no (or prohibit-password). This routine only works after a password has been guessed.
  • Get an alert when any authorized_keys file changes, for example with an auditd watch or file-integrity monitoring.
  • Limit or block repeated failed logins with tools like fail2ban or a cloud firewall rule.

How this data was collected

The Threat Observatory publishes the sensor's numbers with a delay and never shows source addresses, typed passwords or keys. A command pattern is only published if every word is on a fixed list of known commands, flags and paths. Anything else is either replaced by a placeholder or dropped. The figures on this page come from one Observatory snapshot, published 15 October 2026 at 02:00 UTC.

Limits: this is one sensor, one protocol and one week. It doesn't measure how common these attacks are across the internet. A login to a honeypot is not access to a real machine, and a command I recorded is an attempt, not proof it would have worked. Corrections are welcome at contact@vardrsec.com.
